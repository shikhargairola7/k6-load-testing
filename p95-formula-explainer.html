Where the 417ms number comes from

The report calls it p95. It isn't an average, and it isn't the worst time recorded — it's the line between the fastest 95% of requests and the slowest 5%. Below is exactly how that line lands on 417 ms, using the actual 60 token requests from this run.

How the formula reaches 417 ms

Three mechanical steps — no judgment calls, no averaging.

  1. 1Sort all 60 token response times from fastest to slowest.
  2. 2Walk 95% of the way down that sorted list: 0.95 × (60 − 1) = 56.05.
  3. 3Position 56.05 falls between the 57th and 58th fastest times — so the answer is 5% of the way from one to the other.
// generic form
rank  = (p ÷ 100) × (n − 1)
p95   = v[low] + frac × (v[high] − v[low])
 
// this run's token data
rank  = 0.95 × (60 − 1) = 56.05
p95   = 393.60 + 0.05 × (867.16 − 393.60) = 417.28 ms

For the room

p95 = 417 ms is not a defect, and it isn't the "typical" response time either — it's the boundary between the fastest 95% of requests and the slowest 5%.

In this run, that boundary happens to sit right next to one unusually slow request (393.6 ms), nudged up slightly because the very next three requests are each a simulated user's first call — paying a one-time cost to open a new connection (867–884 ms). That's a sample-size effect from only 60 requests, not a fault in the test tool.

The math itself is the same formula behind Excel's PERCENTILE.INC — an industry-standard way of describing "typical worst-case" experience, used the same way by every APM and monitoring vendor.
